# 2단계 사고 과정: 왜 DB 를 넣었고, 어디가 약한가

코드에는 "무엇을 했는지"만 남는다. 이 문서는 "왜 그렇게 했는지"와 "무엇을 일부러 하지 않았는지"를 남긴다.

읽는 순서는 실제로 생각한 순서와 같다. 문제를 먼저 보고, 해결책을 넣고, 그 해결책이 만든 새 문제를 본다.

## 1. 출발점: 서버를 끄면 대화가 사라진다

1단계는 대화를 서버의 메모리에만 들고 있었다.

```
브라우저 ──▶ 서버 (메모리에 기록)
```

서버를 껐다 켜면 기록이 없어진다. 메모리는 프로그램이 끝나면 비워지기 때문이다.

이것이 DB 를 넣은 이유의 전부다. 다른 이유는 없었다.

## 2. 해결: 기록을 디스크에 쓴다

DB(여기서는 PostgreSQL)는 데이터를 디스크에 쓴다. 서버 프로그램이 꺼져도 디스크에 쓴 것은 남는다.

```
브라우저 ──▶ 서버 ──▶ PostgreSQL (디스크에 기록)
```

**"그냥 파일에 쓰면 안 되나?"** 된다. 다만 아래를 직접 만들어야 한다.

- 여러 연결이 동시에 써도 내용이 섞이지 않게 하기
- 메시지마다 겹치지 않는 번호 매기기
- "최근 50개만" 같은 조회

DB 는 이것들을 이미 해 준다. 그래서 파일 대신 DB 를 골랐다.

## 3. DB 가 하는 일과 하지 않는 일

DB 를 넣었다고 모든 것이 DB 를 거치는 것은 아니다.

| 일 | 누가 한다 | 어디에 있나 |
|---|---|---|
| 지금 접속한 사람에게 메시지 전달 | 방송 채널 | 서버 메모리 |
| 나중에 온 사람에게 지난 대화 보여 주기 | DB | 디스크 |
| 메시지에 순번 매기기 | DB | 디스크 |

방송 채널은 "지금 듣고 있는 모두에게 한 번에 뿌리는 통로"다. 지금 접속한 사람에게만 의미가 있으므로 저장할 필요가 없고, 그래서 메모리에 둔다.

## 4. DB 를 넣자 생긴 문제: 중복과 순서

1단계에서는 "지난 대화 복사"와 "방송 구독 시작"을 잠금 하나 안에서 같이 했다. 그래서 그 사이에 온 메시지를 놓치거나 두 번 받는 일이 없었다.

DB 를 넣으니 이 방법을 쓸 수 없게 됐다. DB 에서 읽는 일은 시간이 걸리고, 그동안 잠금을 쥐고 있으면 다른 모든 연결이 멈춘다.

그래서 순서를 이렇게 바꿨다.

1. 방송 구독을 먼저 시작한다.
2. 그다음 DB 에서 지난 대화를 읽는다.

이러면 놓치는 메시지는 없다. 대신 1번과 2번 사이에 온 메시지는 DB 에서 한 번, 방송으로 한 번, **두 번** 온다.

문제가 하나 더 있다. 두 사람이 동시에 보내면 DB 에 저장된 순서와 방송된 순서가 다를 수 있다.

### 해결: 순번

메시지마다 DB 가 매긴 번호(`id`)를 붙여 보낸다.

```json
{"seq": 7, "name": "철수", "body": "안녕"}
```

화면은 서버가 보내 준 순서 대신 이 번호를 믿는다.

- 이미 그린 순번이 또 오면 버린다. → 중복 해결
- 순번이 더 큰 줄이 이미 있으면 그 앞에 끼워 넣는다. → 순서 해결

서버는 여전히 같은 메시지를 두 번 보낼 수 있다. 가려내는 쪽은 화면이다. 서버 쪽에서 완벽하게 막으려 하지 않은 이유는, 뒤 단계에서 서버가 여러 대가 되면 어차피 서버 한 대의 잠금으로는 순서를 보장할 수 없기 때문이다. 순번은 그때도 그대로 통한다.

## 5. 다음 걱정: DB 가 과부하에 걸리면?

걸릴 수 있다. 지금 구조에서는 **DB 속도가 곧 채팅 속도**다.

```
지금:  메시지 받음 ──▶ DB 저장 (끝날 때까지 기다림) ──▶ 방송
```

DB 가 부담을 받는 곳은 세 군데다.

| 곳 | 무슨 일이 일어나나 | 왜 문제인가 |
|---|---|---|
| 메시지를 보낼 때 (`db::save_message`) | 메시지 1개마다 INSERT 1번. 저장이 끝나야 방송한다 | DB 가 100ms 걸리면 모든 메시지가 100ms 늦게 도착한다 |
| 접속할 때 (`db::load_messages`) | 대화를 **전부** 읽는다 | 메시지가 100만 개면 접속할 때마다 100만 줄을 읽는다 |
| 연결 묶음 (`db::connect` 의 `max_connections(5)`) | DB 연결 5개를 돌려 쓴다 | 6번째로 보낸 사람은 앞사람이 끝날 때까지 기다린다 |

가장 중요한 것은 첫 줄이다. 저장을 **기다렸다가** 뿌리기 때문에 DB 가 느려지면 채팅 전체가 느려진다.

### 왜 저장을 먼저 하는가

반대로 "먼저 뿌리고 나중에 저장"하면 빠르다. 하지만 뿌린 뒤 저장에 실패하면, 지금 본 사람과 나중에 온 사람이 서로 다른 대화를 보게 된다. 지금은 빠른 것보다 맞는 것을 골랐다.

순번도 이유다. 순번은 DB 가 저장하면서 매기므로, 저장 전에는 순번이 없다.

## 6. 그런데 왜 지금 고치지 않는가

아직 그 문제를 겪지 않았기 때문이다.

브라우저 두 개로 대화하는 정도라면 PostgreSQL 은 전혀 힘들어하지 않는다. 과부하는 사람과 메시지가 많아져야 보인다.

문제를 보기 전에 해결책을 넣으면 그 해결책은 "그냥 원래 있는 것"이 된다. 왜 있는지 모르는 조각은 고칠 수도, 뺄 수도 없다. 그래서 필요해지는 단계에서 넣는다. (CLAUDE.md 작업 원칙 3번)

각 문제를 어디서 풀 것인지는 정해 두었다.

| 문제 | 해결 | 언제 |
|---|---|---|
| 접속할 때마다 전부 읽는다 | 최근 N개만 읽기 | 2단계 안에서 가능 |
| 저장을 기다리느라 채팅이 느리다 | 저장을 뒤로 뺀다 (Kafka) | 6단계 |
| 메시지 양이 PostgreSQL 에 버겁다 | 대용량 저장소로 옮긴다 (ScyllaDB) | 7단계 |

6단계의 모양은 이렇다.

```
6단계:  메시지 받음 ──▶ 큐에 넣음 ──▶ 방송
                          └──▶ (따로) DB 저장
```

큐는 "할 일을 줄 세워 두는 곳"이다. 서버는 큐에 넣기만 하고 바로 방송하며, 저장은 다른 프로그램이 큐에서 꺼내 천천히 한다.

이때 치르는 값이 있다. 저장 전에 뿌리므로 **DB 가 순번을 매길 수 없다.** 순번을 매기는 방법도 그 단계에서 바뀐다.

## 7. 과부하를 직접 보고 싶다면

지금 구조의 약점은 두 가지 방법으로 눈으로 확인할 수 있다.

- **느린 DB 흉내 내기**: `save_message` 안에 일부러 1초 지연을 넣는다. 메시지가 1초씩 늦게 뜬다. 확인하고 되돌린다.
- **부하 걸기**: 스크립트로 수백 명이 동시에 보내게 하고 지연을 잰다.
