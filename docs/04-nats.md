# 4단계 사고 과정: 서버와 서버를 잇는다

코드에는 "무엇을 했는지"만 남는다. 이 문서는 "왜 그렇게 했는지"와 "무엇을 일부러 하지 않았는지"를 남긴다.

3단계에서 문제를 만났다. 이 단계는 그 문제 하나를 푼다. 새로 등장하는 것은 NATS 하나다.

## 1. 출발점: 절반끼리만 대화가 된다

3단계가 끝났을 때의 모양은 이렇다.

```
                              ┌──▶ 서버 1 (8081) ─┐
브라우저들 ──▶ 로드밸런서 ────┤                   ├──▶ PostgreSQL
              (8080)          └──▶ 서버 2 (8082) ─┘
```

여섯 명이 같은 주소로 같은 방에 들어갔는데, 셋씩 갈려 자기 서버 사람의 말만 보였다.

원인은 방송 채널이다. 방송 채널은 **서버 프로세스의 메모리 안**에 있다. 서버 1의 채널에 넣은 말은 서버 1에 붙은 연결만 받는다. 서버 2는 그런 말이 있었는지조차 모른다.

```
서버 1:  철수 ──▶ [방송 채널 1] ──▶ 철수, 민수
서버 2:                             [방송 채널 2] ──▶ 영희   (아무것도 안 온다)
```

## 2. 무엇이 필요한가

서버 밖에 있고, 모든 서버가 함께 붙어 있는 방송 채널이다.

방송 채널이 하는 일을 다시 보면 두 가지뿐이다. 한쪽에서 넣는다. 듣고 있는 모두가 받는다. 이것을 프로세스 밖에서 해 주는 프로그램이 있으면 된다.

**NATS** 가 그런 프로그램이다. 메시지를 날라 주는 일만 한다.

- 내보내기(publish): "이 주제로 이 메시지를 보낸다"
- 듣기(subscribe): "이 주제의 메시지를 나에게 달라"
- 주제(subject): 메시지에 붙이는 이름표. 점으로 나눠 적는다. 예: `room.1`

저장하지 않는다. 그 순간 듣고 있는 쪽에 전하고 잊는다. 1단계의 방송 채널과 성격이 똑같다.

## 3. 넣은 모양

```
                              ┌──▶ 서버 1 ─┐
브라우저들 ──▶ 로드밸런서 ────┤     ▲▼     ├──▶ PostgreSQL
                              │    NATS    │
                              │     ▲▼     │
                              └──▶ 서버 2 ─┘
```

메시지 하나가 가는 길은 이렇다.

```
철수(서버 1) ─▶ 서버 1: DB 에 저장 ─▶ NATS 에 내보냄 (주제 room.1)
                                          │
                        ┌─────────────────┴─────────────────┐
                        ▼                                   ▼
              서버 1: 방송 채널에 넣음              서버 2: 방송 채널에 넣음
                        ▼                                   ▼
                   철수, 민수                              영희
```

코드에서 바뀐 곳은 두 군데다.

1. **보낼 때** (`ws.rs`): 저장한 뒤 자기 방송 채널에 넣던 것을, NATS 에 내보내는 것으로 바꿨다.
2. **받을 때** (`bus.rs` 의 `relay`): 서버마다 뒤에서 도는 일을 하나 뒀다. NATS 에서 온 메시지를 자기 방송 채널에 옮겨 넣는다.

연결 하나를 맡는 코드(`chat` 함수)의 받는 쪽은 한 줄도 바뀌지 않았다. 여전히 방송 채널만 듣는다. 그 채널에 이제 다른 서버의 말도 흘러 들어올 뿐이다.

### 내 서버 사람에게도 NATS 를 거쳐 보낸다

처음 떠오르는 방법은 "내 방송 채널에도 넣고, NATS 에도 내보낸다"이다. 같은 서버 사람은 바로 받으니 빠르다.

그런데 NATS 는 내보낸 본인에게도 돌려준다. 그러면 같은 서버 사람은 한 번은 바로, 한 번은 NATS 를 돌아서, **두 번** 받는다. 이것을 막으려면 "내가 보낸 것은 버린다"는 표시와 검사가 더 필요하다.

그래서 길을 하나로 했다. 모든 메시지는 NATS 를 거쳐서만 방송 채널에 들어온다. 같은 서버든 다른 서버든 같은 길이라 따로 생각할 것이 없다. 대신 같은 서버 사람도 NATS 를 한 번 다녀오는 만큼 늦게 받는다. (같은 컴퓨터에서는 느낄 수 없는 차이다)

### 주제를 방마다 나눈 이유

주제는 `room.방번호` 로 했다. 서버는 `room.*` (room. 뒤에 무엇이 오든) 을 듣는다.

지금은 모든 서버가 모든 방을 다 듣는다. 그러면 주제를 `chat` 하나로 하고 방 번호를 내용에 넣어도 결과는 같다. 그래도 나눈 것은, 방 번호가 "어디로 갈 메시지인가"라는 이름표의 일이기 때문이다. 내용을 열어 보지 않고 주제만 보고 방을 알 수 있다.

## 4. 순서는 어떻게 되나

두 서버가 거의 동시에 내보내면, 받는 서버마다 도착 순서가 다를 수 있다. 서버 1에서는 A, B 순으로, 서버 2에서는 B, A 순으로.

이것은 따로 고치지 않았다. 2단계에서 넣은 **순번**이 이미 풀어 준다. 순번은 DB 가 매기고, 화면은 도착 순서가 아니라 순번대로 끼워 넣는다. 서버가 한 대일 때는 "접속하는 순간의 중복"을 가리려고 넣은 것이, 여기서 한 번 더 쓰인다.

## 5. NATS 가 꺼지면

직접 꺼 봤다. 가는 서버 8081 에, 나는 서버 8082 에 붙어 있다.

| 상황 | 가 (보낸 사람) | 나 (다른 서버) | DB |
|---|---|---|---|
| NATS 켜짐, 가가 말함 | 봄 | 봄 | 저장됨 |
| NATS 끔, 가가 말함 | **못 봄** | **못 봄** | 저장됨 |
| NATS 다시 켬 | 꺼져 있을 때 한 말이 뒤늦게 옴 | 끝내 안 옴 | |
| 다시 켠 뒤 새로 말함 | 봄 | 봄 | 저장됨 |

읽어 낼 것이 셋이다.

- **보낸 본인도 자기 말을 못 본다.** 길을 하나로 한 값이다. NATS 가 없으면 같은 서버 안에서도 전달이 안 된다.
- **말은 사라지지 않는다.** 저장을 먼저 하기 때문이다. 방을 나갔다 들어오면 DB 에서 읽어 온다. NATS 는 "지금 전하는 일"만 맡고, "남기는 일"은 DB 가 맡는다. 둘의 역할이 갈린다.
- **꺼져 있던 동안의 말은 다른 서버에 끝내 안 온다.** NATS 는 저장하지 않는다. 그 순간 듣고 있지 않던 쪽은 영영 못 받는다. 보낸 서버에는 뒤늦게 왔는데, NATS 라이브러리가 못 보낸 것을 쥐고 있다가 다시 붙자마자 보냈고, 그때 다른 서버는 아직 다시 붙기 전이었기 때문이다.

서버는 NATS 가 다시 켜지면 알아서 다시 붙는다. 서버를 다시 켤 필요는 없다.

로그에 "NATS 에 내보냄"이라고 찍혀도 도착했다는 뜻은 아니다. 꺼져 있는 동안에도 그렇게 찍혔다. "보낼 줄에 세웠다"까지만 안다.

### 일부러 하지 않은 것

- **못 받은 말을 화면이 알아채고 채워 넣기.** 순번이 건너뛴 것을 보고 DB 에 물어보면 되지만, 순번은 모든 방이 함께 써서 건너뛰는 것이 정상이다. 지금 순번으로는 "빠졌다"를 알 수 없다. 방마다 순번을 따로 매겨야 하는데 다른 이야기라 미뤘다.
- **NATS 의 저장 기능(JetStream) 쓰기.** 놓친 말을 다시 받게 해 주지만 새 개념이다. 남기는 일은 이미 DB 가 하고 있다.
- **사람이 있는 방만 듣기.** 지금은 서버가 아무도 없는 방의 메시지도 전부 받아서 버린다. 방과 서버가 적을 때는 문제가 드러나지 않는다.
- **NATS 없이 서버 시작하기.** 꺼져 있으면 DB 때와 같이 시작하지 않는다.

## 6. 직접 확인하는 방법

```bash
docker compose up -d   # PostgreSQL, 로드밸런서, NATS
cargo run              # 터미널 1: 서버 8081
PORT=8082 cargo run    # 터미널 2: 서버 8082
```

1. 브라우저 탭을 네 개쯤 열어 모두 `http://localhost:8080` 으로 들어간다. 탭마다 다른 이름으로 로그인해 `모두의 방`에 들어간다.
2. 상태 줄에서 "서버 8081" 탭과 "서버 8082" 탭이 섞여 있는지 본다.
3. 서로 말을 보낸다. → **어느 서버에 붙었든 전부 보인다.** (3단계에서는 같은 서버끼리만 보였다)
4. `docker compose stop nats` 로 NATS 를 끄고 말을 보낸다. → 아무에게도 안 보인다. 자기 화면에도 안 뜬다.
5. `방 목록으로`를 누르고 다시 들어간다. → 방금 보낸 말이 있다. (DB 에서 읽어 왔다)
6. `docker compose start nats` 로 다시 켠다. 몇 초 뒤 말을 보낸다. → 다시 전부 보인다.

스크립트로 확인한 결과다. 여섯 명이 같은 주소, 같은 방에 들어가 한 마디씩 했다.

| 사람 | 붙은 서버 | 본 사람 |
|---|---|---|
| 가, 다, 마 | 8081 | 가 나 다 라 마 바 |
| 나, 라, 바 | 8082 | 가 나 다 라 마 바 |

같은 말이 두 번 온 사람은 없었다. 다른 서버의 다른 방에 있는 사람에게는 가지 않았다.

## 7. 지금 구조의 한계

- **NATS 가 꺼지면 실시간 전달이 전부 멈춘다.** 같은 서버 안에서도 그렇다. 말은 DB 에 남는다.
- NATS 가 끊긴 동안의 말은 실시간으로는 끝내 안 온다. 다시 들어와야 보인다.
- 모든 서버가 모든 방의 메시지를 받는다. 방과 서버가 늘면 버리는 일이 늘어난다.
- **서버 한 대가 두 가지 일을 다 한다.** 브라우저 연결을 붙들고 있는 일과, 로그인·방·저장 같은 로직이다. 연결이 많아져서 서버를 늘리면 로직도 같이 늘고, 로직을 고쳐 서버를 다시 켜면 붙어 있던 사람이 전부 끊긴다. → 5단계로 가는 이유. 연결 담당과 로직 담당을 나눈다.
