# 5단계 사고 과정: 연결 담당과 로직 담당을 나눈다

코드에는 "무엇을 했는지"만 남는다. 이 문서는 "왜 그렇게 했는지"와 "무엇을 일부러 하지 않았는지"를 남긴다.

4단계의 끝에서 문제를 하나 적어 두었다. 이 단계는 그 문제 하나를 푼다. 새로 등장하는 것은 gRPC 하나다.

## 1. 출발점: 서버 한 대가 두 가지 일을 한다

4단계가 끝났을 때의 모양은 이렇다.

```
                              ┌──▶ 서버 1 ─┐
브라우저들 ──▶ 로드밸런서 ────┤     ▲▼     ├──▶ PostgreSQL
                              │    NATS    │
                              │     ▲▼     │
                              └──▶ 서버 2 ─┘
```

서버 한 대가 하는 일을 적어 보면 성격이 다른 두 가지가 섞여 있다.

| | 붙들고 전하는 일 | 무엇이 옳은지 정하는 일 |
|---|---|---|
| 하는 것 | WebSocket 연결 유지, 메시지 실어 나르기 | 로그인, 방, 저장, 순번 |
| 들고 있는 것 | 연결 수천 개 (끊기면 사용자가 바로 안다) | 없음 (요청마다 DB 에 묻는다) |
| 자주 고치나 | 거의 안 고친다 | 기능을 넣을 때마다 고친다 |
| 늘리는 이유 | 붙어 있는 사람이 많아져서 | 요청이 많아져서 |

### 문제를 직접 본다

`v0.4.0` 에서 해 볼 수 있다. (`git switch main` 후 실행)

1. 서버 두 대를 띄우고 탭 몇 개로 대화한다.
2. 서버 하나를 Ctrl+C 로 껐다가 다시 `cargo run` 한다. 코드 한 줄을 고쳐 다시 켰다고 치자.
3. → 그 서버에 붙어 있던 탭은 전부 **"연결 끊김"** 이 된다.

로그인 문구 하나를 고쳤을 뿐인데 대화하던 사람이 끊긴다. 자주 고치는 코드와 끊기면 안 되는 연결이 한 프로세스에 묶여 있어서다. 서버를 늘릴 때도 같다. 연결이 모자라 한 대를 더 띄우면 로직도 한 벌 더 따라온다.

## 2. 무엇이 필요한가

둘을 다른 프로세스로 떼어 놓는다.

- **게이트웨이** (연결 담당): 브라우저 연결을 붙들고, 메시지를 실어 나르기만 한다. 고칠 일이 적어 오래 켜 둔다.
- **채팅 서버** (로직 담당): 로그인, 방, 저장. 마음껏 고치고 다시 켠다. 붙들고 있는 연결이 없으니 다시 켜도 끊길 사람이 없다.

그런데 떼어 놓으면 새 문제가 생긴다. 지금까지는 연결을 맡은 코드가 `db::save_message(...)` 를 그냥 불렀다. 같은 프로세스 안의 함수였기 때문이다. 다른 프로세스가 되면 함수를 부를 수 없다. 게이트웨이가 채팅 서버에게 "이것 좀 해 줘" 하고 **부탁하고 답을 받는 방법**이 필요하다.

### NATS 로는 왜 안 하나

프로세스 사이를 잇는 것은 이미 하나 있다. NATS 다. 하지만 성격이 다르다.

| | NATS (4단계) | 지금 필요한 것 |
|---|---|---|
| 모양 | 한쪽이 내보내면 듣는 모두가 받는다 | 한쪽이 묻고 한쪽이 답한다 |
| 받는 쪽 | 몇 명인지 모른다. 0명이어도 된다 | 정확히 하나. 없으면 실패다 |
| 답 | 없다. 도착했는지도 모른다 | 꼭 있어야 한다 (입장권이 진짜인가? 순번이 몇 번인가?) |

"입장권 확인해 줘"는 답을 기다려야 하는 일이다. 방송에 대고 물어볼 일이 아니다.

**gRPC** 가 이 일을 한다. 다른 프로세스의 함수를 부르는 방식이다. 부르는 쪽에서는 보통 함수처럼 보인다.

```rust
let reply = state.chat.clone().join(request).await;   // 실제로는 네트워크를 건너갔다 온다
```

## 3. 약속을 먼저 적는다

두 프로그램이 따로 돌기 때문에, 무엇을 보내면 무엇이 돌아오는지를 양쪽이 똑같이 알고 있어야 한다. gRPC 는 이것을 파일 하나에 먼저 적게 한다. `proto/chat.proto` 다.

```proto
service Chat {
  rpc Join(JoinRequest) returns (JoinReply);   // 입장
  rpc Say(SayRequest) returns (SayReply);      // 말하기
}
```

빌드할 때 이 파일에서 Rust 코드가 만들어진다 (`build.rs`). 부탁하는 쪽 코드와 해 주는 쪽 코드가 같은 파일에서 나오므로, 한쪽만 고쳐서 모양이 어긋나는 일이 생기지 않는다. 어긋나면 컴파일이 안 된다.

부탁은 두 가지뿐이다. 예전에 연결을 맡은 코드가 DB 를 건드리던 자리가 정확히 두 군데였기 때문이다.

| 부탁 | 언제 | 채팅 서버가 하는 일 | 돌려주는 것 |
|---|---|---|---|
| `Join` 입장 | WebSocket 을 맺기 직전 | 입장권 확인, 방 확인, 최근 대화 읽기 | 이름, 방 이름, 최근 대화 |
| `Say` 말하기 | 브라우저가 말을 보낼 때마다 | 저장, NATS 에 내보내기 | 순번 |

### 입장을 한 번에 묶은 이유

입장권 확인, 방 확인, 최근 대화 읽기를 따로따로 부탁할 수도 있었다. 그러면 입장 한 번에 네트워크를 세 번 건넌다. 같은 프로세스 안의 함수는 부르는 값이 없지만, 다른 프로세스의 함수는 부를 때마다 왕복이 든다. 그래서 "입장"이라는 뜻 하나로 묶어 한 번에 다녀온다.

묶으면서 순서를 하나 지켜야 했다. 예전에는 연결 코드 안에서 "방송 채널 구독 → 최근 대화 읽기" 순이었다. 읽는 사이에 온 메시지를 놓치지 않으려는 순서다. 지금은 최근 대화가 `Join` 의 답에 실려 오므로, **`Join` 을 부르기 전에** 구독을 시작한다 (`ws.rs`). 그 틈에 온 메시지가 두 번 가는 것은 전과 같이 순번이 가려 준다.

## 4. 넣은 모양

```
                              ┌──▶ 게이트웨이 1 (8081) ──┐
              화면, /ws       │           ▲              │ gRPC
브라우저들 ──▶ 로드밸런서 ────┤          NATS ◀──────────┼──────── 채팅 서버 ──▶ PostgreSQL
              (8080)          │           ▼              │        (8090, 50051)
                   │          └──▶ 게이트웨이 2 (8082) ──┘              ▲
                   └──────────────── /login, /rooms ────────────────────┘
```

메시지 하나가 가는 길은 이렇다.

```
철수 ─WebSocket─▶ 게이트웨이 1 ─gRPC Say─▶ 채팅 서버: DB 에 저장 ─▶ NATS 에 내보냄 (주제 room.1)
                                                                        │
                                              ┌─────────────────────────┴──────────┐
                                              ▼                                    ▼
                                    게이트웨이 1: 방송 채널                게이트웨이 2: 방송 채널
                                              ▼                                    ▼
                                         철수, 민수                               영희
```

4단계와 달라진 것은 가운데 한 칸이다. "저장하고 NATS 에 내보내는 일"이 게이트웨이 밖으로 나갔다. NATS 에서 받아 뿌리는 아래쪽 절반은 한 줄도 바뀌지 않았다.

누가 무엇을 아는지가 갈렸다.

| | 게이트웨이 | 채팅 서버 |
|---|---|---|
| WebSocket | 안다 | 모른다 |
| PostgreSQL | **모른다** | 안다 |
| NATS | 받기만 한다 | 내보내기만 한다 |
| 파일 | `src/bin/gateway/` | `src/bin/chat/` |

둘이 함께 쓰는 것(gRPC 약속, NATS 다루기)은 `src/lib.rs` 에 있다.

### 로그인과 방은 게이트웨이를 거치지 않는다

`/login`, `/rooms` 요청은 로드밸런서가 채팅 서버로 바로 보낸다 (`deploy/nginx.conf`). 한 번 묻고 답하면 끝나는 요청이라 붙들고 있을 연결이 없다. 게이트웨이를 거치게 하면 게이트웨이는 받은 것을 그대로 넘기는 일만 하게 되고, 방 기능을 고칠 때마다 게이트웨이도 같이 고쳐야 한다. 그러면 나눈 뜻이 없다.

그래서 채팅 서버에는 문이 두 개다. 브라우저용 HTTP (8090) 와 게이트웨이용 gRPC (50051).

### 프로젝트는 하나, 프로그램은 둘

폴더를 두 프로젝트로 쪼개지 않았다. `src/bin/` 아래 폴더 하나가 프로그램 하나가 되는 cargo 의 규칙을 썼다. 그래서 실행 명령에 어느 쪽인지 적는다: `cargo run --bin chat`, `cargo run --bin gateway`.

## 5. 채팅 서버가 꺼지면

직접 꺼 봤다. 일곱 명이 두 게이트웨이에 나뉘어 붙어 있다.

| 상황 | 붙어 있던 연결 | 말하기 | 새로 입장 | 로그인, 방 목록 |
|---|---|---|---|---|
| 채팅 서버 켜짐 | 유지 | 됨 | 됨 | 됨 |
| 채팅 서버 끔 | **유지** | 안 됨 | 안 됨 | 안 됨 (502) |
| 채팅 서버 다시 켬 | **유지** | 다시 됨 | 됨 | 됨 |

읽어 낼 것이 셋이다.

- **연결은 한 번도 끊기지 않았다.** 이 단계에서 얻으려던 것이다. 4단계에서는 서버를 다시 켜면 붙어 있던 사람이 전부 끊겼다.
- **꺼져 있는 동안 한 말은 사라진다.** 저장할 곳에 닿지 못했기 때문이다. 4단계에서 NATS 가 꺼졌을 때는 "저장은 됐고 전달만 안 됐다"였는데, 이번에는 저장도 안 된다. 게이트웨이 로그에 "보내지 못함"이 찍히고, 화면에는 아무 표시가 없다.
- **게이트웨이를 다시 켤 필요가 없다.** gRPC 연결은 처음 부를 때 맺고, 끊기면 다음에 부를 때 다시 맺게 해 두었다 (`connect_lazy`). 그래서 켜는 순서도 상관없다.

### 일부러 하지 않은 것

- **보내지 못한 말을 화면에 알리기, 다시 보내기.** 지금은 조용히 사라진다. 화면에 알림을 그리는 일과 재시도는 따로 다룰 이야기다.
- **채팅 서버 여러 대.** 한 대만 띄운다. 붙든 연결이 없어서 여러 대로 늘리기는 쉽지만, 아직 한 대로 모자란 것을 보지 못했다.
- **게이트웨이가 정말 게이트웨이인지 확인하기.** 채팅 서버는 gRPC 로 온 요청을 그대로 믿는다. `Say` 에 적힌 이름도 믿는다. gRPC 포트(50051)에 닿을 수 있으면 누구든 남의 이름으로 말할 수 있다. 실제 서비스에서는 이 포트를 밖에 열지 않고, 서로를 확인하는 장치를 둔다.
- **입장권을 말할 때마다 다시 확인하기.** 입장할 때 한 번 확인하고, 그 뒤로는 게이트웨이가 기억한 이름을 쓴다.
- **gRPC 의 다른 기능들.** 줄줄이 이어 받기(streaming), 제한 시간, 재시도 설정. 묻고 답하기 하나만 썼다.

## 6. 직접 확인하는 방법

protoc 가 필요하다. 없으면 `brew install protobuf`.

```bash
docker compose up -d                   # PostgreSQL, 로드밸런서, NATS
docker compose restart lb              # 전 단계에서 켜 둔 로드밸런서가 있으면 새 설정을 읽힌다
cargo run --bin chat                   # 터미널 1: 채팅 서버
cargo run --bin gateway                # 터미널 2: 게이트웨이 8081
PORT=8082 cargo run --bin gateway      # 터미널 3: 게이트웨이 8082
```

1. 브라우저 탭을 네 개쯤 열어 모두 `http://localhost:8080` 으로 들어간다. 탭마다 다른 이름으로 로그인해 `모두의 방`에 들어간다.
2. 서로 말을 보낸다. → 어느 게이트웨이에 붙었든 전부 보인다. 터미널 1(채팅 서버)에 `[말하기]` 가, 터미널 2·3 에 `받음`과 `전달`이 찍힌다. 말 하나가 세 프로그램을 거쳐 가는 것이 보인다.
3. 터미널 1 에서 Ctrl+C 로 **채팅 서버를 끈다.** → 탭의 상태 줄이 "연결됨" 그대로다. 끊기지 않는다.
4. 그 상태에서 말을 보낸다. → 아무에게도 안 보인다. 게이트웨이 터미널에 `보내지 못함`이 찍힌다.
5. `cargo run --bin chat` 으로 다시 켠다. 탭을 새로고침하지 않고 말을 보낸다. → **다시 전부 보인다.**
6. 견주어 보려면 게이트웨이 하나를 Ctrl+C 로 꺼 본다. → 그쪽에 붙은 탭은 "연결 끊김"이 된다. 끊기면 안 되는 쪽이 어느 쪽인지 보인다.

스크립트로 확인한 결과다. 여섯 명이 같은 주소, 같은 방에 들어가 한 마디씩 했다.

| 확인한 것 | 결과 |
|---|---|
| 여섯 명이 두 게이트웨이에 셋씩 나뉨 | 됨 |
| 모두가 여섯 마디를 한 번씩 받음 (두 번 온 것 없음) | 됨 |
| 다른 방 사람에게는 안 감 | 됨 |
| 늦게 온 사람이 지난 대화를 받음, 이전 대화 더 보기 | 됨 |
| 가짜 입장권 401, 없는 방 404 | 됨 |
| 채팅 서버를 껐다 켜는 동안 연결 일곱 개 유지 | 됨 |
| 다시 켠 뒤 같은 연결로 대화 | 됨 |

## 7. 지금 구조의 한계

- **채팅 서버가 꺼져 있는 동안 한 말은 사라진다.** 화면에 알리지도 않는다.
- 채팅 서버는 한 대다. 꺼지면 말하기, 입장, 로그인이 모두 멈춘다. (붙어 있는 연결만 남는다)
- 게이트웨이와 채팅 서버 사이에 서로를 확인하는 장치가 없다.
- **말 한 마디가 DB 저장이 끝날 때까지 기다린다.** `Say` 는 저장을 마쳐야 답하고, 게이트웨이는 그 답을 기다린다. 순서가 "저장 → NATS → 화면"이라서, DB 가 느려지면 그만큼 모든 말이 늦게 뜬다. DB 가 1초 걸리면 채팅이 1초씩 밀린다. 저장은 "남기는 일"이고 전달은 "지금 전하는 일"인데, 지금은 전하는 일이 남기는 일 뒤에 줄을 서 있다. → 6단계로 가는 이유. 저장을 뒤로 빼서 따로 하게 한다.
