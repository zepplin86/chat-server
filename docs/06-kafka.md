# 6단계 사고 과정: 저장을 뒤로 뺀다

코드에는 "무엇을 했는지"만 남는다. 이 문서는 "왜 그렇게 했는지"와 "무엇을 일부러 하지 않았는지"를 남긴다.

5단계의 끝에서 문제를 하나 적어 두었다. 이 단계는 그 문제 하나를 푼다. 새로 등장하는 것은 Kafka 다.

먼저 밝혀 둔다. 이 단계에는 Kafka 말고 바뀌는 것이 하나 더 있다. **순번을 채팅 서버가 직접 매긴다.** 한 단계에 새 개념은 하나라는 원칙에서 벗어나지만 떼어 놓을 수 없었다. 지금까지 순번은 DB 가 매겼는데, 저장을 뒤로 빼면 말하는 순간에는 DB 에 넣지 않으므로 DB 에게 순번을 받을 수 없다. 저장을 미루는 것과 순번을 다른 데서 얻는 것은 한 몸이다. (3절)

## 1. 출발점: 말 한 마디가 DB 를 기다린다

5단계가 끝났을 때 메시지 하나가 가는 길은 이렇다.

```
철수 ─▶ 게이트웨이 ─gRPC Say─▶ 채팅 서버: DB 에 저장 ─▶ NATS 에 내보냄 ─▶ 게이트웨이들 ─▶ 화면
                                          └── 여기가 끝나야 다음으로 간다
```

순서가 "저장 → 전달"이다. 저장이 끝나야 전달이 시작된다.

### 문제를 직접 본다

`v0.5.0` 에서 쟀다. 두 사람이 같은 방에 있고, 한 사람이 말한 뒤 다른 사람 화면에 뜰 때까지의 시간이다. DB 를 느리게 만드는 대신 잠깐 멈췄다 (`docker compose pause postgres`).

| 상황 | 말이 뜨기까지 |
|---|---|
| DB 정상 | 14 ms |
| DB 를 3초 멈춤 | **3170 ms** |

DB 가 멈춘 만큼 채팅이 멈춘다. 채팅 서버도, 게이트웨이도, NATS 도 멀쩡한데 말이 안 간다.

직접 해 보려면: `git switch main` (v0.5.0) 으로 띄우고, 탭 두 개로 대화하다가 `docker compose pause postgres` 를 친다. 말을 보내면 화면에 안 뜬다. `docker compose unpause postgres` 를 치는 순간 한꺼번에 뜬다.

## 2. 무엇이 필요한가

4단계에서 이미 적었다. 저장은 "남기는 일"이고 전달은 "지금 전하는 일"이다. 둘은 급한 정도가 다르다.

- 전달은 지금 당장이어야 한다. 1초 늦으면 대화가 안 된다.
- 저장은 조금 늦어도 된다. 다음에 방에 들어올 때까지만 들어가 있으면 된다.

그러니 급한 쪽이 느린 쪽을 기다리지 않게 한다. 전달을 먼저 하고, 저장은 뒤에서 따로 한다.

그런데 "뒤에서 따로"가 "잊어버려도 된다"는 아니다. 채팅 서버가 "나중에 저장해야지" 하고 메모리에 쥐고 있다가 꺼지면 그 말은 사라진다. 화면에는 떴는데 다시 들어오면 없는 말이 된다. 그래서 **저장할 것을 잃어버리지 않게 맡아 둘 곳**이 필요하다.

- 빨리 받아 줄 것. (느리면 DB 를 기다리는 것과 다를 바 없다)
- 받은 것은 잃어버리지 않을 것. 디스크에 적어 둘 것.
- 저장하는 쪽이 꺼져 있었어도, 다시 켜지면 못 가져간 것부터 이어서 가져갈 수 있을 것.

### NATS 로는 왜 안 하나

| | NATS | 지금 필요한 것 |
|---|---|---|
| 받은 것을 | 전하고 잊는다 | 적어 두고 남긴다 |
| 듣는 쪽이 꺼져 있으면 | 그동안의 것은 영영 못 받는다 | 켜지면 못 읽은 곳부터 이어서 읽는다 |

4단계에서 NATS 를 껐을 때 "꺼져 있던 동안의 말은 끝내 안 온다"를 봤다. 화면에 뿌리는 일은 그래도 됐다. 저장은 그러면 안 된다.

**Kafka** 가 이 일을 한다. 받은 것을 순서대로 디스크에 적어 두는 프로그램이다. 끝에 덧붙이기만 하는 긴 공책이라고 보면 된다.

- 토픽(topic): 공책 한 권의 이름. `chat.messages` 한 권만 쓴다.
- 기록(record): 공책에 적힌 한 줄. 메시지 하나다.
- 오프셋(offset): 그 줄이 몇 번째 줄인지. 읽는 쪽은 "나는 몇 번째 줄까지 읽었다"를 Kafka 에 적어 둔다. 그래서 껐다 켜도 이어서 읽는다.

DB 보다 빠른 이유는 하는 일이 적어서다. 찾기 좋게 정리하지도, 겹치는지 확인하지도 않는다. 끝에 적기만 한다.

## 3. 순번은 누가 매기나

지금까지는 메시지를 DB 에 넣으면 DB 가 1, 2, 3... 을 붙여 돌려줬다. 그 순번을 붙여 화면에 보냈다.

이제 화면에 보낼 때는 아직 DB 에 넣기 전이다. DB 에게 물어볼 수 없다. (물어보려고 기다리면 다시 DB 를 기다리는 것이다)

그래서 채팅 서버가 직접 매긴다 (`src/bin/chat/seq.rs`). 순번이 지켜야 할 것은 둘이다. 겹치지 않을 것, 나중 것이 더 클 것. 시각이 이 둘을 거의 다 채워 준다.

```
순번 = 1970년부터 지금까지의 밀리초 × 1000
       같은 밀리초에 또 오면 직전 순번 + 1
```

예: `1795147630553000`, `1795147630553001`, `1795147630563000`

- 서버를 껐다 켜도 그사이 시간이 흘렀으므로 예전 것보다 크다. 어디에 적어 둘 필요가 없다.
- 예전에 DB 가 매긴 순번(1, 2, 3...)보다 훨씬 크다. 지난 대화 뒤에 자연스럽게 이어진다.
- 화면(JavaScript)이 정확히 다룰 수 있는 수의 한계(약 9000조) 안이다.

순번이 1씩 늘지 않고 건너뛴다. 화면은 순번을 "순서 맞추기"와 "중복 가리기"에만 쓰므로 상관없다.

## 4. 넣은 모양

```
                              ┌──▶ 게이트웨이 1 ──┐
              화면, /ws       │        ▲          │ gRPC
브라우저들 ──▶ 로드밸런서 ────┤       NATS ◀──────┼────── 채팅 서버 ──읽기──▶ PostgreSQL
              (8080)          │        ▼          │           │                  ▲
                   │          └──▶ 게이트웨이 2 ──┘           │ 적기             │ 넣기
                   │                                          ▼                  │
                   │                                        Kafka ──읽기──▶ 저장 담당
                   └────────── /login, /rooms ──▶ 채팅 서버
```

메시지 하나가 가는 길은 이렇다.

```
철수 ─▶ 게이트웨이 ─gRPC Say─▶ 채팅 서버: 순번 매김 ─▶ Kafka 에 적음 ─▶ NATS 에 내보냄 ─▶ 화면
                                                            │
                                                            ▼ (나중에, 따로)
                                                       저장 담당 ─▶ PostgreSQL
```

프로그램이 하나 늘었다. **저장 담당** (`src/bin/persist/`) 이다. Kafka 를 읽어 DB 에 넣는 일 하나만 한다. 아무도 이 프로그램을 부르지 않는다. 문을 열지 않는다.

채팅 서버는 이제 메시지를 DB 에 넣지 않는다. DB 는 읽을 때만 쓴다 (로그인, 방, 지난 대화).

### Kafka 에 적는 것은 기다린다

"저장 → 전달"을 "전달 → 저장"으로 그냥 뒤집지는 않았다. 채팅 서버는 Kafka 가 "적었다"고 답할 때까지 기다린 뒤에 NATS 에 내보낸다. 적지 못하면 내보내지 않는다.

2단계에서 정한 원칙이 그대로다. 남기지 못한 말은 뿌리지 않는다. 달라진 것은 "남겼다"의 뜻이다. 전에는 DB 에 들어간 것이었고, 이제는 Kafka 에 적힌 것이다. Kafka 에 적혔으면 DB 에는 언젠가 들어간다.

### 저장 담당은 같은 것을 두 번 읽을 수 있다

저장 담당의 순서는 "읽는다 → DB 에 넣는다 → 여기까지 읽었다고 Kafka 에 적는다"이다.

"읽었다"를 먼저 적으면 안 된다. 적고 나서 DB 에 넣기 전에 꺼지면, 그 메시지는 읽은 것으로 쳐서 다시 안 온다. 영영 DB 에 없다.

넣은 뒤에 적으면 반대 일이 생긴다. 넣고 나서 적기 전에 꺼지면, 다시 켰을 때 같은 메시지를 한 번 더 읽는다. 이쪽은 막을 수 있다. 순번이 같은 것이 이미 있으면 넣지 않는다 (`ON CONFLICT (id) DO NOTHING`). 두 번 읽어도 한 줄만 남는다.

잃어버리는 것과 두 번 하는 것 중 하나를 골라야 하면, 두 번 해도 괜찮게 만들고 두 번 하는 쪽을 고른다.

## 5. 하나씩 꺼 보면

직접 꺼 봤다.

| 끈 것 | 실시간 대화 | DB 에 남나 | 다시 켜면 |
|---|---|---|---|
| (다 켜짐) | 됨 | 곧 들어감 | |
| 저장 담당 | **됨** | 그동안은 안 들어감 | 밀린 것을 전부 넣는다 |
| PostgreSQL (멈춤) | **됨** (22 ms) | 그동안은 안 들어감 | 밀린 것을 전부 넣는다 |
| Kafka | 안 됨 | — | 다시 된다 |

같은 측정을 다시 했다.

| 상황 | 5단계 | 6단계 |
|---|---|---|
| DB 정상 | 14 ms | 약 20 ms |
| DB 를 3초 멈춤 | 3170 ms | **22 ms** |

읽어 낼 것이 셋이다.

- **DB 가 멈춰도 대화는 멈추지 않는다.** 이 단계에서 얻으려던 것이다.
- **DB 가 정상일 때는 조금 느려졌다.** 거치는 곳이 하나 늘었기 때문이다. 평소의 몇 ms 를 내주고, DB 가 느릴 때 같이 느려지지 않는 것을 얻었다.
- **기댈 곳이 DB 에서 Kafka 로 옮겨 갔다.** Kafka 가 꺼지면 말하기가 멈춘다 (5초 기다린 뒤 실패). 없어진 것이 아니라 더 빠르고 단순한 쪽으로 옮긴 것이다.

### 일부러 하지 않은 것

- **방금 한 말을 지난 대화에 채워 넣기.** 저장 담당이 넣기 전에 방에 들어온 사람은 그 말을 지난 대화에서 못 받는다. 저장 담당을 끄고 확인했다: 다섯 마디가 오간 방에 새로 들어온 사람이 받은 지난 대화는 0개였다. 평소에는 틈이 몇 ms 라 잘 보이지 않는다. 채우려면 최근 메시지를 어딘가에 따로 쥐고 있어야 하는데, 다른 이야기라 미뤘다.
- **채팅 서버 여러 대.** 순번을 시각으로 매기므로, 두 대가 같은 밀리초에 매기면 겹친다. 여러 대로 가려면 순번에 "몇 번 서버인지"를 섞어야 한다.
- **공책을 여러 갈래로 나누기(파티션).** 한 갈래만 쓴다. 저장 담당도 한 대다.
- **묶어서 넣기.** 저장 담당은 한 번에 하나씩 넣는다. 여러 개를 모아 한 번에 넣으면 훨씬 빠르지만, 아직 하나씩으로 모자란 것을 보지 못했다.
- **Kafka 에 쌓인 기록 지우기.** Kafka 의 기본 설정대로 둔다 (일주일 뒤 지워진다). DB 에 들어간 뒤로는 필요 없는 기록이다.

## 6. 직접 확인하는 방법

cmake 가 필요하다 (Kafka 라이브러리 빌드용). 없으면 `brew install cmake`. 처음 빌드는 몇 분 걸린다.

```bash
docker compose up -d                   # PostgreSQL, 로드밸런서, NATS, Kafka
cargo run --bin chat                   # 터미널 1: 채팅 서버
cargo run --bin persist                # 터미널 2: 저장 담당
cargo run --bin gateway                # 터미널 3: 게이트웨이 8081
PORT=8082 cargo run --bin gateway      # 터미널 4: 게이트웨이 8082
```

1. 브라우저 탭 두 개로 `http://localhost:8080` 에 들어가 같은 방에서 대화한다. 터미널 1 에 `Kafka 에 적고 NATS 에 내보냄`, 터미널 2 에 `[저장] 순번 ...` 이 찍힌다. 말 하나가 두 갈래로 가는 것이 보인다.
2. `docker compose pause postgres` 로 **DB 를 멈춘다.** 말을 보낸다. → **바로 뜬다.** 터미널 2 는 조용하다. (5단계에서는 여기서 말이 멈췄다)
3. `docker compose unpause postgres`. → 터미널 2 에 밀린 `[저장]` 이 한꺼번에 찍힌다.
4. 터미널 2 에서 Ctrl+C 로 **저장 담당을 끈다.** 말을 몇 마디 보낸다. → 바로 뜬다.
5. `방 목록으로`를 누르고 다시 들어간다. → 방금 한 말이 **없다.** 아직 DB 에 안 들어갔다.
6. `cargo run --bin persist` 로 다시 켠다. → 밀린 `[저장]` 이 찍힌다. 방에 다시 들어가면 있다.
7. `docker compose stop kafka`. 말을 보낸다. → 안 뜬다. 5초쯤 뒤 터미널 1 에 `Kafka 에 적지 못해 내보내지 않음`이 찍힌다. `docker compose start kafka` 하고 10초쯤 뒤에는 다시 된다.

스크립트로 확인한 결과다.

| 확인한 것 | 결과 |
|---|---|
| 저장 담당이 꺼져 있어도 실시간으로 받음 | 됨 |
| 순번이 커지는 순서이고 겹치지 않음 | 됨 |
| 저장 담당을 켜면 밀린 것이 DB 에 들어감 | 됨 |
| 저장 담당을 껐다 켜면 이어서 읽음, 두 번 넣지 않음 | 됨 |
| DB 가 멈춰 있어도 말이 바로 감 (22 ms) | 됨 |
| DB 가 돌아오면 멈춘 동안의 말이 DB 에 들어감 | 됨 |
| Kafka 가 꺼지면 말이 가지 않음, 연결은 유지, 다시 켜면 됨 | 됨 |
| 5단계에서 확인한 열다섯 가지 | 그대로 됨 |

## 7. 지금 구조의 한계

- **방금 한 말이 지난 대화에 없을 수 있다.** 저장 담당이 밀려 있는 만큼 그렇다.
- Kafka 가 꺼지면 말하기가 멈춘다.
- 채팅 서버는 한 대여야 한다. 두 대면 순번이 겹칠 수 있다.
- 저장 담당이 갑자기 죽으면(Ctrl+C 가 아니라), 다시 켠 뒤 6초쯤 지나야 읽기 시작한다. Kafka 가 죽은 쪽을 그만큼 기다려 준다.
- **메시지는 여전히 전부 PostgreSQL 한 곳에 쌓인다.** 저장을 뒤로 뺐을 뿐, 넣는 곳은 그대로다. 저장 담당은 메시지 하나마다 PostgreSQL 에 한 줄을 넣는다. 들어오는 말이 넣는 속도보다 많아지면 밀린 양이 계속 늘고, "방금 한 말이 지난 대화에 없는" 틈도 같이 길어진다. 표 하나가 한 컴퓨터 안에서 끝없이 커지는 것도 그대로다. → 7단계로 가는 이유. 메시지를 많이 쓰고 많이 쌓는 데 맞는 저장소로 옮긴다.
