# 7단계 사고 과정: 메시지를 ScyllaDB 로 옮긴다

코드에는 "무엇을 했는지"만 남는다. 이 문서는 "왜 그렇게 했는지"와 "무엇을 일부러 하지 않았는지"를 남긴다.

6단계의 끝에서 문제를 하나 적어 두었다. 새로 등장하는 것은 ScyllaDB 하나다.

> **이 문서는 진행 중의 기록이다.** 옮기는 일은 끝났고 잘 돈다. 그런데 재 보니 기대만큼 빨라지지 않았다. 5절에 잰 값을 그대로 적었다.

## 1. 출발점: 저장이 전달을 따라가지 못한다

6단계에서 저장을 뒤로 뺐다. 전달은 저장을 기다리지 않는다. 그 대신 저장이 얼마나 뒤처지는지가 새로 궁금해진다.

### 문제를 직접 본다

`v0.6.0` 에서 쟀다. 스무 명이 한 방에서 쉬지 않고 말을 보낸다. "전부 화면에 뜰 때까지"와 "전부 저장소에 들어갈 때까지"를 따로 쟀다.

| 보낸 양 | 전달 끝 | 저장 끝 | 저장이 늦은 시간 |
|---|---|---|---|
| 10,000개 | 7.5초 (초당 1,332개) | 49.4초 (초당 202개) | 41.9초 |
| 50,000개 | 37.5초 (초당 1,332개) | 256.7초 (초당 195개) | **219.2초** |

전달은 초당 1,300개쯤 하는데 저장은 초당 200개쯤 한다. 말이 계속 들어오면 밀린 양이 끝없이 는다. 5만 개를 보냈을 때 마지막 말은 화면에 뜨고 나서 3분 39초 뒤에야 저장소에 들어갔다.

밀린 동안 생기는 일은 6단계에서 봤다. 방에 새로 들어온 사람이 방금 오간 말을 지난 대화에서 못 받는다.

### 왜 느린가

저장 담당은 메시지 하나마다 PostgreSQL 에 한 줄을 넣는다. PostgreSQL 은 한 줄을 넣을 때마다 "디스크에 확실히 적혔다"를 확인하고 답한다. 한 번에 약 5 ms 다. 1초에 200번이 한계인 셈이다.

이것은 PostgreSQL 이 못나서가 아니다. 넣은 것은 절대 잃지 않겠다는 약속을 지키는 값이다. 계정이나 방처럼 가끔 바뀌는 것에는 맞는 약속이다. 1초에 수천 개씩 끝없이 쌓이는 메시지에는 무겁다.

## 2. 무엇이 필요한가

메시지라는 자료는 성격이 뚜렷하다.

- 넣기만 한다. 고치거나 지우는 일이 거의 없다.
- 끝없이 쌓인다.
- 읽는 방법이 하나뿐이다. "이 방의, 이 순번보다 앞의 50개."
- 다른 표와 엮어 읽지 않는다. (계정·방과 JOIN 하지 않는다)

**ScyllaDB** 는 이런 자료에 맞춰 만들어진 DB 다. 많이 쓰고 많이 쌓는 쪽에 맞춰져 있고, 컴퓨터를 여러 대로 늘려 나눠 담을 수 있다. 대신 PostgreSQL 처럼 아무 질문이나 던질 수는 없다.

계정·입장권·방은 PostgreSQL 에 그대로 둔다. 가끔 바뀌고, 서로 엮여 있고, 겹치면 안 되는 것들(같은 이름의 계정)이라 PostgreSQL 이 맞다. 저장소를 자료의 성격에 따라 둘로 나눈 것이다.

## 3. 표를 질문에 맞춰 만든다

PostgreSQL 과 생각하는 순서가 반대다.

- PostgreSQL: 표를 먼저 만들고, 나중에 아무 질문이나 던진다. DB 가 알아서 찾는다.
- ScyllaDB: 던질 질문을 먼저 정하고, 그 질문에 맞게 표를 만든다.

우리 질문은 "이 방의, 이 순번보다 앞의 50개" 하나다. 그래서 이렇게 만들었다 (`src/store.rs`).

```sql
CREATE TABLE chat.messages (
    room_id bigint,
    seq     bigint,
    name    text,
    body    text,
    PRIMARY KEY ((room_id), seq)
) WITH CLUSTERING ORDER BY (seq DESC)
```

- `(room_id)` 는 **묶는 기준**이다 (파티션 키). 같은 방의 메시지를 한 덩어리로 모아 둔다. 방 번호를 알면 그 덩어리가 어디 있는지 바로 안다. 다른 방의 메시지는 들여다보지 않는다.
- `seq` 는 덩어리 안에서 **줄 세우는 기준**이다 (클러스터링 키). 순번 순서로 나란히 놓인다.
- `seq DESC` 는 최근 것을 앞에 둔다는 뜻이다. "가장 최근 50개"는 덩어리 앞에서 50개를 집으면 끝난다.

```
방 1 덩어리:  [순번 905] [순번 904] [순번 903] ...     ← 앞에서 50개
방 2 덩어리:  [순번 871] [순번 850] ...
```

### 두 번 넣어도 한 줄

ScyllaDB 의 INSERT 는 "없으면 넣고, 있으면 덮어쓴다"이다. 같은 방, 같은 순번으로 두 번 넣으면 같은 줄을 같은 내용으로 덮어쓸 뿐이다.

6단계에서 저장 담당은 같은 메시지를 두 번 읽을 수 있다고 했다. 그때는 `ON CONFLICT DO NOTHING` 으로 걸렀다. 이제는 거를 필요가 없다. 그 확인 코드가 없어졌다.

## 4. 넣은 모양

```
                              ┌──▶ 게이트웨이 1 ──┐
              화면, /ws       │        ▲          │ gRPC              ┌─▶ PostgreSQL (계정, 입장권, 방)
브라우저들 ──▶ 로드밸런서 ────┤       NATS ◀──────┼────── 채팅 서버 ──┤
              (8080)          │        ▼          │           │       └─▶ ScyllaDB (지난 대화 읽기)
                   │          └──▶ 게이트웨이 2 ──┘           │ 적기             ▲
                   │                                          ▼                  │ 넣기
                   │                                        Kafka ──읽기──▶ 저장 담당
                   └────────── /login, /rooms ──▶ 채팅 서버
```

바뀐 것은 세 군데다.

1. **저장 담당**: 넣는 곳이 PostgreSQL 에서 ScyllaDB 로 바뀌었다. 이제 PostgreSQL 을 모른다.
2. **채팅 서버**: 지난 대화를 ScyllaDB 에서 읽는다 (입장할 때, 이전 대화 더 보기). 계정·방은 여전히 PostgreSQL.
3. **옮기는 도구** (`src/bin/migrate/`): PostgreSQL 에 쌓여 있던 옛 메시지를 ScyllaDB 로 복사한다. 한 번만 돌린다.

게이트웨이, NATS, Kafka, 화면은 한 줄도 바뀌지 않았다. 저장소가 바뀐 것을 모른다. 6단계에서 저장을 뒤로 빼 둔 덕에 바꿀 곳이 좁았다.

### 옛 메시지 옮기기

옮기는 도구를 돌렸다. PostgreSQL 60,082개 → ScyllaDB 60,082개. 1분 45초 걸렸다 (초당 570개쯤).

PostgreSQL 의 `messages` 표는 지우지 않았다. 읽기만 했다. 여러 번 돌려도 덮어쓰기라 줄이 늘지 않는다.

## 5. 재 보니

같은 측정을 다시 했다.

| 보낸 양 | 저장소 | 전달 끝 | 저장 끝 | 저장이 늦은 시간 |
|---|---|---|---|---|
| 10,000개 | PostgreSQL | 7.5초 | 49.4초 (초당 202개) | 41.9초 |
| 10,000개 | ScyllaDB | 8.4초 | 30.8초 (초당 324개) | 22.5초 |
| 50,000개 | PostgreSQL | 37.5초 | 256.7초 (초당 195개) | 219.2초 |
| 50,000개 | ScyllaDB | 43.3초 | 157.5초 (초당 318개) | **114.1초** |

조용한 방에 들어갈 때 지난 대화를 받는 시간은 둘 다 15~50 ms 로, 차이를 가릴 수 없었다.

**저장은 1.6배 빨라졌다. 그런데 여전히 전달을 따라가지 못한다.** 초당 320개 대 초당 1,200개다. 밀리는 속도가 줄었을 뿐 밀리는 것은 그대로다. 이 단계가 풀려던 문제는 풀리지 않았다.

### 왜 이것밖에 안 되나

저장소만 바꿨고, **넣는 방식은 그대로**이기 때문이다. 저장 담당은 여전히 이렇게 돈다.

```
하나 읽는다 → 하나 넣는다 → 답을 기다린다 → "읽었다"고 적는다 → 다음 하나
```

한 번에 하나씩, 앞의 것이 끝나야 다음 것을 한다. 저장소가 아무리 빨라도 한 줄로 서서 왕복하는 시간이 한계가 된다. 옮기는 도구가 초당 570개였던 것과 견주면, 저장 담당의 초당 320개에는 저장소 말고도 메시지마다 로그를 찍고 Kafka 에 "읽었다"를 적는 시간이 들어 있다.

ScyllaDB 가 잘하는 것은 "하나를 빨리"가 아니라 "여럿을 동시에"와 "여러 대로 나눠서"다. 한 줄로 서서 넣으면 그 장점을 쓰지 못한다.

그리고 지금 환경에서는 볼 수 없는 것이 있다. ScyllaDB 를 고르는 큰 이유는 컴퓨터를 여러 대로 늘려 방(덩어리)을 나눠 담는 것인데, 여기서는 한 대를, 그것도 CPU 1개와 메모리 750MB 로 묶어 돌린다. 이 숫자로 "ScyllaDB 가 PostgreSQL 보다 몇 배 빠르다"를 말할 수는 없다.

### 아직 하지 않은 것

- **여러 개를 동시에 넣기.** 저장 담당이 Kafka 에서 여러 개를 한꺼번에 읽어 동시에 넣고, 전부 끝나면 "여기까지 읽었다"를 한 번만 적는다. 위에서 본 병목을 푸는 길이다. 아직 하지 않았고, 해 보지 않았으므로 얼마나 빨라질지도 모른다.
- **덩어리 나누기.** 방 하나의 메시지가 덩어리 하나에 끝없이 쌓인다. 아주 큰 방은 덩어리가 너무 커진다. 순번 구간별로 덩어리를 쪼개는 방법이 있다.
- **PostgreSQL 의 옛 `messages` 표 지우기.** 그대로 두었다.
- **언제 말했는지(시각) 저장하기.** 예전 표에는 있었는데 옮기면서 뺐다. 순번에 시각이 들어 있다.
- **ScyllaDB 여러 대.** 한 대다.

## 6. 직접 확인하는 방법

```bash
docker compose up -d                   # PostgreSQL, ScyllaDB, 로드밸런서, NATS, Kafka
                                       # ScyllaDB 는 처음 켤 때 1분쯤 걸린다
cargo run --bin migrate                # 옛 메시지를 ScyllaDB 로 옮긴다 (한 번만)
cargo run --bin chat                   # 터미널 1: 채팅 서버
cargo run --bin persist                # 터미널 2: 저장 담당
cargo run --bin gateway                # 터미널 3: 게이트웨이 8081
PORT=8082 cargo run --bin gateway      # 터미널 4: 게이트웨이 8082
```

1. `http://localhost:8080` 으로 들어가 예전에 대화하던 방에 들어간다. → 지난 대화가 그대로 보인다. (옮기는 도구를 돌리지 않았다면 비어 있다)
2. 말을 보낸다. 방을 나갔다 들어온다. → 방금 한 말이 있다.
3. ScyllaDB 에 직접 물어본다.
   ```bash
   docker compose exec scylla cqlsh -e "SELECT seq, name, body FROM chat.messages WHERE room_id = 1 LIMIT 5"
   ```
   → 방금 한 말이 맨 위에 있다. `ORDER BY` 를 쓰지 않았는데 최근 것부터 나온다.
4. 방 번호 없이 물어본다.
   ```bash
   docker compose exec scylla cqlsh -e "SELECT * FROM chat.messages WHERE name = '철수'"
   ```
   → **거절당한다.** 어느 덩어리를 볼지(방 번호) 알려 주지 않았기 때문이다. 질문에 맞춰 표를 만든다는 것이 이것이다.
5. `docker compose pause scylla` 후 말을 보낸다. → 바로 뜬다. `unpause` 하면 밀린 것이 들어간다. (6단계에서 PostgreSQL 로 한 것과 같다)

스크립트로 확인한 결과다.

| 확인한 것 | 결과 |
|---|---|
| 5단계에서 확인한 열다섯 가지 (대화, 방 격리, 지난 대화, 이전 대화 더 보기 등) | 그대로 됨 |
| 저장 담당이 꺼져 있어도 대화됨, 켜면 밀린 것이 들어감 | 됨 |
| 저장 담당을 껐다 켜면 이어서 읽음, 줄이 늘지 않음 | 됨 |
| ScyllaDB 가 멈춰 있어도 말이 바로 감 (22 ms), 돌아오면 들어감 | 됨 |
| Kafka 가 꺼지면 말이 가지 않음, 연결은 유지 | 됨 |
| Kafka 를 다시 켜면 다시 됨 | 됐지만 15초 넘게 걸렸다. 6단계에서는 15초 안에 됐다 |
| 옛 메시지 60,082개 옮기기, 개수 일치 | 됨 |

## 7. 지금 구조의 한계

- **저장이 여전히 전달보다 느리다.** 초당 320개 대 1,200개. 말이 몰리면 밀리고, 밀린 만큼 "방금 한 말이 지난 대화에 없다". 한 번에 하나씩 넣는 방식이 병목이다. (5절)
- 방 하나의 메시지가 덩어리 하나에 끝없이 쌓인다.
- ScyllaDB 는 켜지는 데 오래 걸리고 메모리를 많이 쓴다. 내 컴퓨터에서 돌리는 것이 다섯 개가 됐다.
- 한 대로는 ScyllaDB 를 고른 이유(여러 대로 나눠 담기)를 볼 수 없다.
