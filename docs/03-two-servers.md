# 3단계 사고 과정: 서버를 한 대 더 띄우면 무엇이 깨지는가

코드에는 "무엇을 했는지"만 남는다. 이 문서는 "왜 그렇게 했는지"와 "무엇을 일부러 하지 않았는지"를 남긴다.

3단계는 해결책을 넣는 단계가 아니다. **문제를 만나는 단계**다. 같은 서버를 한 대 더 띄워 보고, 한 대일 때는 보이지 않던 것이 무엇인지 본다.

## 1. 출발점: 서버가 한 대뿐이다

2단계가 끝났을 때의 모양은 이렇다.

```
브라우저들 ──▶ 서버 (1대) ──▶ PostgreSQL
```

서버 한 대가 받을 수 있는 사람 수에는 끝이 있다. 그리고 이 서버가 죽으면 채팅 전체가 멈춘다.

가장 먼저 떠오르는 방법은 같은 서버를 한 대 더 띄우는 것이다.

```
브라우저 A ──▶ 서버 1 ─┐
                       ├──▶ PostgreSQL
브라우저 B ──▶ 서버 2 ─┘
```

## 2. 첫 걸음: 포트를 밖에서 정한다

**안 되던 것**: 서버가 8080 포트를 쓰도록 코드에 박혀 있었다. 포트는 한 컴퓨터 안에서 프로그램을 구분하는 번호이고, 한 포트는 한 프로그램만 쓸 수 있다. 그래서 같은 컴퓨터에서 두 대를 띄울 수 없었다.

**넣은 것**: `PORT` 환경 변수로 포트를 정할 수 있게 했다. 없으면 전처럼 8080 이다.

```bash
PORT=8080 cargo run   # 터미널 1
PORT=8081 cargo run   # 터미널 2
```

이것이 이번 걸음에서 일부러 넣은 것의 전부다. 나머지는 띄워 보고 알게 된 것이다.

## 3. 띄워 보니: 그대로 되는 것

두 서버는 서로를 모른다. 그런데도 아래는 손대지 않고 그대로 됐다.

| 되는 것 | 왜 되는가 |
|---|---|
| 서버 1에서 만든 계정으로 서버 2에 로그인 | 계정이 DB 에 있다 |
| 서버 1에서 받은 입장권으로 서버 2에 접속 | 입장권이 DB 에 있다 |
| 서버 1에서 만든 방이 서버 2의 목록에 보임 | 방이 DB 에 있다 |
| 서버 1에서 보낸 말을 서버 2에서 **다시 입장하면** 볼 수 있음 | 메시지가 DB 에 있다 |
| 순번이 두 서버에 걸쳐 겹치지 않음 | 순번을 DB 가 매긴다 |

공통점은 하나다. **DB 에 둔 것은 두 서버가 함께 본다.**

2단계에서 입장권을 서버 메모리가 아니라 DB 에 둔 것, 순번을 서버가 세지 않고 DB 에 맡긴 것이 여기서 값을 했다. 서버 메모리에 두었다면 "서버 1에서 로그인했는데 서버 2는 나를 모른다"가 됐을 것이다.

## 4. 띄워 보니: 깨지는 것 (1) 서버끼리 부딪힌다

두 서버를 **동시에** 켜니 한 대가 켜지다 죽었다.

```
duplicate key value violates unique constraint "rooms_name_key"
Key (name)=(모두의 방) already exists.
```

서버는 켜질 때 "방이 하나도 없으면 '모두의 방'을 만든다"를 한다. 두 서버가 같은 순간에 이것을 했다.

```
서버 1: 방이 있나? → 없다
서버 2: 방이 있나? → 없다      ← 서버 1이 아직 만들기 전이다
서버 1: '모두의 방' 을 만든다 → 성공
서버 2: '모두의 방' 을 만든다 → 실패 (같은 이름이 이미 있다)
```

"확인하고, 그다음에 만든다"는 두 걸음이다. 혼자일 때는 그 사이에 아무도 끼어들지 않는다. 둘이 되면 끼어든다.

1단계에서 같은 일을 겪었다. 여러 연결이 대화 기록을 동시에 건드려서 잠금(`Mutex`)으로 감쌌다. 그때는 한 프로그램 안의 일이라 프로그램 안의 잠금으로 충분했다. 지금은 **서로 다른 프로그램** 사이의 일이다. 서버 1의 잠금을 서버 2는 볼 수 없다.

### 고친 방법

두 서버가 함께 보는 곳은 DB 뿐이다. 그래서 잠금도 DB 에서 빌린다(`pg_advisory_xact_lock`). 표를 준비하는 일 전체를 한 묶음(트랜잭션)으로 만들고, 그 묶음을 한 번에 한 서버만 하게 했다. 나중에 온 서버는 기다렸다가 들어가서, 이미 다 만들어진 것을 보고 그냥 지나간다.

빈 DB 에서 서버 4대를 동시에 켜는 것을 5번 해 보았고, 5번 모두 4대가 다 켜졌다.

### 여기서 배운 것

이것은 계획에 없던 문제다. 서버를 띄워 보기 전에는 몰랐다. 그리고 이 문제의 모양은 앞으로 계속 나온다.

> 한 대일 때는 "프로그램 안"에서 해결되던 것이, 여러 대가 되면 "프로그램 밖"에서 해결되어야 한다.

## 5. 띄워 보니: 깨지는 것 (2) 서로의 말이 안 보인다

이것이 3단계의 본론이다.

철수는 서버 1(8080)에, 영희는 서버 2(8081)에 붙어 같은 방에 들어갔다. 각자 한마디씩 했다.

| | 실시간으로 본 것 |
|---|---|
| 철수 (서버 1) | 자기 말만 |
| 영희 (서버 2) | 자기 말만 |
| 영희가 방을 나갔다 다시 들어옴 | 철수의 말과 자기 말 둘 다 |

같은 방에 있는데 서로의 말이 보이지 않는다. 나갔다 들어오면 보인다.

### 왜 그런가

메시지가 가는 길은 둘이다. (2단계 문서 3번)

| 길 | 어디에 있나 | 두 서버가 함께 보나 |
|---|---|---|
| 저장: 나중에 온 사람에게 보여 줄 기록 | DB | 본다 |
| 전달: 지금 접속한 사람에게 뿌리기 | 방송 채널 (서버 메모리) | **못 본다** |

방송 채널은 서버의 메모리에 있다. 서버마다 자기 것이 하나씩 있고, 서로 이어져 있지 않다.

```
철수 ──▶ 서버 1 [방송 채널 1] ──▶ 서버 1에 붙은 사람들
              │
              └──저장──▶ PostgreSQL ◀──저장──┐
                                             │
영희 ──▶ 서버 2 [방송 채널 2] ──▶ 서버 2에 붙은 사람들
```

철수의 말은 방송 채널 1에 들어간다. 영희는 방송 채널 2를 듣고 있다. 그래서 오지 않는다. DB 에는 저장됐으므로 다시 들어오면(DB 에서 읽으면) 보인다.

4번과 같은 모양이다. 한 대일 때 "프로그램 안"(메모리의 방송 채널)에서 해결되던 전달이, 두 대가 되자 "프로그램 밖"에서 해결되어야 하게 됐다.

### 왜 지금 고치지 않는가

이것을 푸는 것이 4단계다. 서버들 사이에 메시지를 날라 주는 것이 따로 필요하다.

"DB 를 계속 들여다보면 되지 않나?"라는 생각이 들 수 있다. 각 서버가 "새 메시지가 있나?"를 DB 에 자꾸 물어보는 방법이다. 된다. 다만 얼마나 자주 묻느냐가 곧 메시지가 늦는 시간이 되고, 자주 물을수록 새 메시지가 없을 때도 DB 가 일을 한다. 2단계에서 본 대로 DB 는 이미 가장 바쁜 곳이다.

## 6. 직접 확인하는 방법

```bash
docker compose up -d
PORT=8080 cargo run   # 터미널 1
PORT=8081 cargo run   # 터미널 2
```

1. 브라우저에서 `http://localhost:8080` 을 열고 `철수`로 로그인해 `모두의 방`에 들어간다.
2. 다른 탭에서 `http://localhost:8081` 을 열고 `영희`로 로그인해 `모두의 방`에 들어간다.
3. 서로 말을 보낸다. → 상대의 말이 보이지 않는다.
4. 영희가 `방 목록으로`를 누르고 다시 들어간다. → 철수의 말이 보인다.

두 터미널의 로그를 보면 각 서버가 자기에게 붙은 사람에게만 `전달`하는 것이 보인다.

## 7. 지금 구조의 한계

- **다른 서버에 붙은 사람끼리 실시간으로 대화가 안 된다.** → 4단계로 가는 이유
- 어느 서버에 붙을지를 사람이 주소(포트)로 고른다. 실제로는 주소가 하나여야 하고, 들어온 사람을 서버들에 나눠 보내는 것이 앞에 있어야 한다. → 3단계의 다음 걸음 (로드밸런서)
